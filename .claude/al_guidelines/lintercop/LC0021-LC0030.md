# LinterCop Rules LC0021-LC0030

## LC0021: Confirm Implement Confirm Management (Info)

**Rule**: Confirm() must be implemented through the "Confirm Management" codeunit.

**Why**: Using the Confirm Management codeunit instead of direct Confirm() calls allows for:
- Suppression during batch processing
- Consistent behavior across the application
- Testability (can be mocked in unit tests)

**Instruction**: Replace direct Confirm() calls with Confirm Management codeunit.

**Correct Example**:
```al
procedure DeleteRecord()
var
    ConfirmManagement: Codeunit "Confirm Management";
begin
    if ConfirmManagement.GetResponseOrDefault(DeleteConfirmQst, true) then
        Rec.Delete(true);
end;

var
    DeleteConfirmQst: Label 'Do you want to delete this record?';
```

**Incorrect Example**:
```al
procedure DeleteRecord()
begin
    if Confirm(DeleteConfirmQst) then  // VIOLATION: Use Confirm Management
        Rec.Delete(true);
end;
```

## LC0022: GlobalLanguage Implement Translation Helper (Info)

**Rule**: GlobalLanguage() must be implemented through the "Translation Helper" codeunit.

**Why**: The Translation Helper codeunit provides proper language switching with automatic restoration, preventing language context issues.

**Instruction**: Use Translation Helper codeunit for language operations.

**Correct Example**:
```al
procedure GetTranslatedDescription(): Text
var
    TranslationHelper: Codeunit "Translation Helper";
    SavedLanguage: Integer;
begin
    SavedLanguage := TranslationHelper.SetGlobalLanguageToDefault();
    // Do work in default language
    Result := GetDescription();
    TranslationHelper.RestoreGlobalLanguage(SavedLanguage);
    exit(Result);
end;
```

**Incorrect Example**:
```al
procedure GetTranslatedDescription(): Text
var
    SavedLanguage: Integer;
begin
    SavedLanguage := GlobalLanguage();  // VIOLATION: Use Translation Helper
    GlobalLanguage(1033);
    Result := GetDescription();
    GlobalLanguage(SavedLanguage);
    exit(Result);
end;
```

## LC0023: Always Specify Fieldgroups (Info)

**Rule**: Fieldgroup "{0}" is missing on table "{1}".

**Why**: FieldGroups control how records appear in lookups (DropDown) and tiles (Brick). Missing these groups results in poor user experience.

**Instruction**: ALWAYS define DropDown and Brick fieldgroups on tables that will be displayed in the UI.

**Correct Example**:
```al
table 50100 "VOL Product Category"
{
    Caption = 'Product Category';

    fields
    {
        field(1; "Code"; Code[20])
        {
            Caption = 'Code';
        }
        field(2; Description; Text[100])
        {
            Caption = 'Description';
        }
        field(3; "Parent Category"; Code[20])
        {
            Caption = 'Parent Category';
        }
    }

    fieldgroups
    {
        fieldgroup(DropDown; "Code", Description)
        {
        }
        fieldgroup(Brick; "Code", Description, "Parent Category")
        {
        }
    }
}
```

**Incorrect Example**:
```al
table 50100 "VOL Product Category"
{
    Caption = 'Product Category';

    fields { ... }

    // VIOLATION: Missing fieldgroups section
}
```

## LC0024: Semicolon After Method Or Trigger Declaration (Info)

**Rule**: Procedure or Trigger declaration should not end with semicolon.

**Why**: In modern AL syntax, procedure and trigger declarations should not have a trailing semicolon. This is a legacy C/AL pattern that is no longer recommended.

**Instruction**: Remove semicolons from procedure and trigger declarations.

**Correct Example**:
```al
procedure CalculateAmount()
begin
    // Implementation
end;

trigger OnInsert()
begin
    // Implementation
end;
```

**Incorrect Example**:
```al
procedure CalculateAmount();  // VIOLATION: Remove semicolon
begin
    // Implementation
end;

trigger OnInsert();  // VIOLATION: Remove semicolon
begin
    // Implementation
end;
```

## LC0025: Internal Procedure Modifier (Hidden)

**Rule**: Procedure must be either local, internal or define a documentation comment.

**Why**: Public procedures without documentation become part of your API surface. They should either be:
- Made local (not accessible outside the object)
- Made internal (accessible within extension but not outside)
- Documented (indicating intentional public API)

**Instruction**: All procedures should be either local, internal, or have XML documentation.

**Correct Example**:
```al
/// <summary>
/// Calculates the total amount for the sales order.
/// </summary>
/// <param name="SalesHeader">The sales header to calculate for.</param>
/// <returns>The calculated total amount.</returns>
procedure CalculateTotalAmount(SalesHeader: Record "Sales Header"): Decimal
begin
    // Public, documented procedure
end;

local procedure ValidateCustomer(CustomerNo: Code[20])
begin
    // Private procedure - only used in this object
end;

internal procedure GetInternalConfig(): Record "VOL Setup"
begin
    // Internal - accessible within extension only
end;
```

**Incorrect Example**:
```al
procedure CalculateTotalAmount(SalesHeader: Record "Sales Header"): Decimal
begin
    // VIOLATION: Public without documentation - is this intentional API?
end;
```

## LC0026: ToolTip Must End With Dot (Info)

**Rule**: ToolTip must end with a dot.

**Why**: Consistent punctuation in tooltips improves professionalism and readability.

**Instruction**: ALL ToolTip values must end with a period.

**Correct Example**:
```al
field("Customer No."; Rec."Customer No.")
{
    ToolTip = 'Specifies the customer number for this document.';
}
```

**Incorrect Example**:
```al
field("Customer No."; Rec."Customer No.")
{
    ToolTip = 'Specifies the customer number for this document';  // VIOLATION: Missing period
}
```

## LC0027: RunPage Implement Page Management (Info)

**Rule**: Utilize the "Page Management" codeunit for launching page.

**Why**: Page Management codeunit provides:
- Standard page types based on table configuration
- Consistent navigation behavior
- Proper handling of card vs list pages

**Instruction**: Use Page Management codeunit for page navigation.

**Correct Example**:
```al
procedure ShowCustomer()
var
    Customer: Record Customer;
    PageManagement: Codeunit "Page Management";
begin
    if Customer.Get(CustomerNo) then
        PageManagement.PageRun(Customer);
end;
```

**Incorrect Example**:
```al
procedure ShowCustomer()
var
    Customer: Record Customer;
begin
    if Customer.Get(CustomerNo) then
        Page.Run(Page::"Customer Card", Customer);  // VIOLATION: Use Page Management
end;
```

## LC0028: Identifiers In Event Subscribers (Info)

**Rule**: Event subscriber arguments now use identifier syntax instead of string literals.

**Why**: Using identifier syntax provides compile-time validation, IntelliSense support, and automatic updates when objects are renamed.

**Instruction**: Use identifier syntax (ObjectType::ObjectName) in event subscriber attributes.

**Correct Example**:
```al
[EventSubscriber(ObjectType::Codeunit, Codeunit::"Sales-Post", OnBeforePostSalesDoc, '', false, false)]
local procedure HandleOnBeforePostSalesDoc(var SalesHeader: Record "Sales Header")
begin
    // Implementation
end;
```

**Incorrect Example**:
```al
[EventSubscriber(ObjectType::Codeunit, 80, 'OnBeforePostSalesDoc', '', false, false)]
// VIOLATION: Use Codeunit::"Sales-Post" instead of 80
// VIOLATION: Use identifier 'OnBeforePostSalesDoc' not string
local procedure HandleOnBeforePostSalesDoc(var SalesHeader: Record "Sales Header")
begin
    // Implementation
end;
```

## LC0029: Compare DateTime Through Codeunit (Info)

**Rule**: Use CompareDateTime method in Type Helper codeunit for DateTime comparisons.

**Why**: DateTime comparisons can be tricky due to precision and timezone issues. The Type Helper codeunit provides reliable comparison methods.

**Instruction**: Use Type Helper codeunit for DateTime comparisons.

**Correct Example**:
```al
procedure IsOrderOlderThan(SalesHeader: Record "Sales Header"; CompareDate: DateTime): Boolean
var
    TypeHelper: Codeunit "Type Helper";
begin
    exit(TypeHelper.CompareDateTime(SalesHeader."Order Date", CompareDate) < 0);
end;
```

**Incorrect Example**:
```al
procedure IsOrderOlderThan(SalesHeader: Record "Sales Header"; CompareDate: DateTime): Boolean
begin
    exit(SalesHeader."Order Date" < CompareDate);  // VIOLATION: Use Type Helper
end;
```

## LC0030: Access Internal For Install And Upgrade Codeunits (Info)

**Rule**: Set Access property to Internal for Install/Upgrade codeunits.

**Why**: Install and Upgrade codeunits are called automatically by the system and should never be called by external extensions. Making them Internal prevents misuse.

**Instruction**: ALWAYS set Access = Internal on Install and Upgrade codeunits.

**Correct Example**:
```al
codeunit 50100 "VOL Install"
{
    Subtype = Install;
    Access = Internal;  // MANDATORY for Install codeunits

    trigger OnInstallAppPerCompany()
    begin
        SetupDefaultData();
    end;
}

codeunit 50101 "VOL Upgrade"
{
    Subtype = Upgrade;
    Access = Internal;  // MANDATORY for Upgrade codeunits

    trigger OnUpgradePerCompany()
    begin
        UpgradeData();
    end;
}
```

**Incorrect Example**:
```al
codeunit 50100 "VOL Install"
{
    Subtype = Install;
    // VIOLATION: Missing Access = Internal

    trigger OnInstallAppPerCompany()
    begin
        SetupDefaultData();
    end;
}
```
