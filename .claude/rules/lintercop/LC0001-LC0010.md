# LinterCop Rules LC0001-LC0010

## LC0001: FlowFields Should Not Be Editable (Warning)

**Rule**: FlowFields should not be editable.

**Why**: FlowFields are calculated fields that pull data from related tables. Making them editable would allow users to enter values that would be immediately overwritten by the calculated value, causing confusion and data integrity issues.

**Instruction**: When creating table fields with `FieldClass = FlowField`, ALWAYS set `Editable = false`.

**Correct Example**:
```al
field(50; "Total Amount"; Decimal)
{
    Caption = 'Total Amount';
    FieldClass = FlowField;
    CalcFormula = sum("Sales Line".Amount where("Document No." = field("No.")));
    Editable = false;  // MANDATORY for FlowFields
}
```

**Incorrect Example**:
```al
field(50; "Total Amount"; Decimal)
{
    Caption = 'Total Amount';
    FieldClass = FlowField;
    CalcFormula = sum("Sales Line".Amount where("Document No." = field("No.")));
    // Missing Editable = false - VIOLATION
}
```

## LC0002: Commit Must Be Explained By Comment (Warning)

**Rule**: Commit() needs a comment to justify its existence.

**Why**: Commit() forces a database transaction commit, which can cause data integrity issues if not used carefully. A comment explaining WHY the commit is necessary helps future developers understand the design decision.

**Instruction**: ALWAYS add a comment before or after any Commit() call explaining why it is necessary.

**Correct Example**:
```al
procedure ProcessOrder()
begin
    // Commit required to release locks before calling external web service
    Commit();
    CallExternalService();
end;
```

**Incorrect Example**:
```al
procedure ProcessOrder()
begin
    Commit();  // VIOLATION: No explanation for why Commit is needed
    CallExternalService();
end;
```

## LC0003: Do Not Use Object IDs In Variables Or Properties (Warning)

**Rule**: Do not use an Object ID for properties or variables declaration. Use the object name instead.

**Why**: Using object names instead of IDs makes code more readable and maintainable. Object names are self-documenting, while IDs require looking up what object they refer to.

**Instruction**: ALWAYS use object names (with quotes if needed) instead of numeric object IDs in variable declarations and properties.

**Correct Example**:
```al
var
    Customer: Record Customer;
    SalesHeader: Record "Sales Header";

page 50100 "My List Page"
{
    SourceTable = Customer;  // Use name, not ID
}
```

**Incorrect Example**:
```al
var
    Customer: Record 18;  // VIOLATION: Use "Customer" not 18
    SalesHeader: Record 36;  // VIOLATION: Use "Sales Header" not 36

page 50100 "My List Page"
{
    SourceTable = 18;  // VIOLATION: Use Customer not 18
}
```

## LC0004: LookupPageId And DrillDownPageId Must Be Set (Warning)

**Rule**: Property "LookupPageID" and "DrillDownPageID" must be filled in table.

**Why**: When users click on fields that reference this table, BC needs to know which page to show. Without these properties, the system cannot provide drill-down functionality.

**Instruction**: For tables that will be referenced by other tables via TableRelation, ALWAYS set LookupPageID and DrillDownPageID properties.

**Correct Example**:
```al
table 50100 "VOL Product Category"
{
    Caption = 'Product Category';
    LookupPageId = "VOL Product Categories";
    DrillDownPageId = "VOL Product Categories";

    fields
    {
        field(1; "Code"; Code[20])
        {
            Caption = 'Code';
        }
    }
}
```

**Incorrect Example**:
```al
table 50100 "VOL Product Category"
{
    Caption = 'Product Category';
    // VIOLATION: Missing LookupPageId and DrillDownPageId

    fields
    {
        field(1; "Code"; Code[20])
        {
            Caption = 'Code';
        }
    }
}
```

## LC0005: Variable Casing Must Match Declaration (Warning)

**Rule**: Wrong casing detected! The casing of identifiers must match their declaration.

**Why**: Inconsistent casing makes code harder to read and can cause confusion. AL is case-insensitive at runtime but proper casing improves readability.

**Instruction**: ALWAYS use the exact same casing as the original declaration for:
- Variable names
- Procedure names
- Field names
- Object names
- Built-in methods and keywords

**Correct Example**:
```al
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.SetRange("Document Type", SalesHeader."Document Type"::Order);
    SalesHeader.FindFirst();  // Correct casing
end;
```

**Incorrect Example**:
```al
var
    SalesHeader: Record "Sales Header";
begin
    salesheader.SetRange("Document Type", SalesHeader."Document Type"::Order);  // VIOLATION
    SalesHeader.FINDFIRST();  // VIOLATION: Should be FindFirst()
end;
```

## LC0006: Field Not AutoIncrement In Temporary Table (Error)

**Rule**: AutoIncrement fields are not possible in temporary tables!

**Why**: Temporary tables exist only in memory and don't have database sequences. AutoIncrement relies on database-level ID generation which doesn't work for temporary tables.

**Instruction**: NEVER use AutoIncrement = true on fields in tables with TableType = Temporary. Use a different approach like manual numbering.

**Correct Example**:
```al
table 50100 "VOL Temp Buffer"
{
    TableType = Temporary;

    fields
    {
        field(1; "Entry No."; Integer)
        {
            Caption = 'Entry No.';
            // No AutoIncrement for temporary tables
        }
    }
}

// Manual numbering in code:
procedure AddEntry()
var
    TempBuffer: Record "VOL Temp Buffer" temporary;
    NextEntryNo: Integer;
begin
    if TempBuffer.FindLast() then
        NextEntryNo := TempBuffer."Entry No." + 1
    else
        NextEntryNo := 1;
    TempBuffer."Entry No." := NextEntryNo;
    TempBuffer.Insert();
end;
```

**Incorrect Example**:
```al
table 50100 "VOL Temp Buffer"
{
    TableType = Temporary;

    fields
    {
        field(1; "Entry No."; Integer)
        {
            Caption = 'Entry No.';
            AutoIncrement = true;  // ERROR: Not allowed in temporary tables
        }
    }
}
```

## LC0007: DataPerCompany Should Always Be Set (Hidden/Info)

**Rule**: DataPerCompany is missing!

**Why**: The DataPerCompany property determines whether table data is shared across all companies or isolated per company. Explicitly setting this property prevents confusion and unintended data sharing.

**Instruction**: ALWAYS explicitly set DataPerCompany on tables. Default is true (data per company), but make it explicit.

**Correct Example**:
```al
table 50100 "VOL Sales Setup"
{
    Caption = 'Sales Setup';
    DataPerCompany = true;  // Explicit - data is company-specific

    fields { ... }
}

table 50101 "VOL Global Config"
{
    Caption = 'Global Configuration';
    DataPerCompany = false;  // Explicit - data is shared across companies

    fields { ... }
}
```

## LC0008: No Filter Operators In SetRange (Warning)

**Rule**: Filter operators should not be used in SetRange. Use SetFilter instead.

**Why**: SetRange is designed for simple equality or range comparisons. Using filter operators like '*', '..', '|' in SetRange can cause unexpected behavior. SetFilter is designed to handle complex filter expressions.

**Instruction**: Use SetRange for simple values and ranges. Use SetFilter for complex patterns with operators.

**Correct Example**:
```al
// Simple value - use SetRange
Customer.SetRange("Customer Posting Group", 'DOMESTIC');

// Range - use SetRange
SalesHeader.SetRange("Posting Date", StartDate, EndDate);

// Pattern with wildcard - use SetFilter
Customer.SetFilter(Name, '@*smith*');

// Multiple values - use SetFilter
Customer.SetFilter("Customer Posting Group", 'DOMESTIC|EXPORT');
```

**Incorrect Example**:
```al
// VIOLATION: Using filter operator in SetRange
Customer.SetRange(Name, '*smith*');  // Should use SetFilter

// VIOLATION: Using multiple values in SetRange
Customer.SetRange("Customer Posting Group", 'DOMESTIC|EXPORT');  // Should use SetFilter
```

## LC0009: Code Metrics Info (Info)

**Rule**: Cyclomatic complexity: {0} (threshold >={1}), Maintainability index: {2}

**Why**: High cyclomatic complexity indicates code that is hard to test and maintain. The maintainability index helps identify code that may need refactoring.

**Instruction**: Keep procedures simple. If cyclomatic complexity exceeds 8 (default threshold), consider:
- Breaking the procedure into smaller, focused procedures
- Simplifying conditional logic
- Using polymorphism instead of complex if/else chains

**Guidelines**:
- Cyclomatic Complexity < 8: Good
- Cyclomatic Complexity 8-15: Consider refactoring
- Cyclomatic Complexity > 15: Needs refactoring
- Maintainability Index > 20: Good
- Maintainability Index < 20: Needs attention

## LC0010: Code Metrics Warning (Warning)

**Rule**: Cyclomatic complexity exceeds threshold.

**Why**: Overly complex procedures are difficult to understand, test, and maintain. They often indicate code that should be broken into smaller units.

**Instruction**: When this warning appears, refactor the procedure:

**Before (Complex)**:
```al
procedure ProcessOrder(var SalesHeader: Record "Sales Header")
begin
    if SalesHeader."Document Type" = SalesHeader."Document Type"::Order then begin
        if SalesHeader.Status = SalesHeader.Status::Open then begin
            if SalesHeader."Sell-to Customer No." <> '' then begin
                if CheckCreditLimit(SalesHeader) then begin
                    if CheckInventory(SalesHeader) then begin
                        PostOrder(SalesHeader);
                    end else
                        Error('Insufficient inventory');
                end else
                    Error('Credit limit exceeded');
            end else
                Error('Customer required');
        end else
            Error('Order must be open');
    end else
        Error('Invalid document type');
end;
```

**After (Refactored)**:
```al
procedure ProcessOrder(var SalesHeader: Record "Sales Header")
begin
    ValidateOrderForProcessing(SalesHeader);
    PostOrder(SalesHeader);
end;

local procedure ValidateOrderForProcessing(SalesHeader: Record "Sales Header")
begin
    ValidateDocumentType(SalesHeader);
    ValidateOrderStatus(SalesHeader);
    ValidateCustomer(SalesHeader);
    ValidateCreditLimit(SalesHeader);
    ValidateInventory(SalesHeader);
end;

local procedure ValidateDocumentType(SalesHeader: Record "Sales Header")
begin
    if SalesHeader."Document Type" <> SalesHeader."Document Type"::Order then
        Error('Invalid document type');
end;
// ... similar small validation procedures
```
