# LinterCop Rules LC0061-LC0070

## LC0061: Set ODataKeyFields With SystemId Field (Info)

**Rule**: Pages of type API must have 'ODataKeyFields' property set to SystemId.

**Why**: Using SystemId as the OData key ensures:
- Unique, immutable record identification
- Consistent behavior across all APIs
- Compatibility with Power Platform and other integrations

**Instruction**: ALL API pages must set ODataKeyFields = SystemId.

**Correct Example**:
```al
page 50100 "VOL Customer API"
{
    PageType = API;
    Caption = 'Customer API';
    APIPublisher = 'volpublisher';
    APIGroup = 'sales';
    APIVersion = 'v1.0';
    EntityName = 'customer';
    EntitySetName = 'customers';
    SourceTable = Customer;
    ODataKeyFields = SystemId;  // MANDATORY for API pages
    DelayedInsert = true;

    layout
    {
        area(Content)
        {
            repeater(General)
            {
                field(id; Rec.SystemId)  // Expose SystemId as 'id'
                {
                    Caption = 'Id';
                    Editable = false;
                }
                field(number; Rec."No.")
                {
                    Caption = 'Number';
                }
            }
        }
    }
}
```

**Incorrect Example**:
```al
page 50100 "VOL Customer API"
{
    PageType = API;
    SourceTable = Customer;
    ODataKeyFields = "No.";  // VIOLATION: Use SystemId

    // or missing entirely:
    // VIOLATION: ODataKeyFields not set
}
```

## LC0062: Mandatory Field Missing On Api Page (Info)

**Rule**: Field 'Rec.{0}' exposed with the name '{1}' should always be included on API Pages.

**Why**: Certain fields are essential for API functionality:
- SystemId for record identification
- SystemCreatedAt/SystemModifiedAt for change tracking
- Primary key fields for reference

**Instruction**: Always include mandatory fields on API pages.

**Correct Example**:
```al
page 50100 "VOL Sales Order API"
{
    PageType = API;
    SourceTable = "Sales Header";
    ODataKeyFields = SystemId;

    layout
    {
        area(Content)
        {
            repeater(General)
            {
                // Mandatory fields
                field(id; Rec.SystemId)
                {
                    Caption = 'Id';
                    Editable = false;
                }
                field(lastModifiedDateTime; Rec.SystemModifiedAt)
                {
                    Caption = 'Last Modified Date Time';
                    Editable = false;
                }
                // Business fields
                field(number; Rec."No.")
                {
                    Caption = 'Number';
                }
                field(customerNumber; Rec."Sell-to Customer No.")
                {
                    Caption = 'Customer Number';
                }
            }
        }
    }
}
```

## LC0063: Give Field More Descriptive Name (Info)

**Rule**: Consider naming field with a more descriptive name: '{0}'.

**Why**: API field names should be clear and self-documenting. Generic names like "code" or "value" don't convey meaning.

**Instruction**: Use descriptive, camelCase names for API fields that clearly indicate their purpose.

**Correct Example**:
```al
page 50100 "VOL Item API"
{
    PageType = API;
    SourceTable = Item;

    layout
    {
        area(Content)
        {
            repeater(General)
            {
                field(itemNumber; Rec."No.")  // Descriptive
                {
                    Caption = 'Item Number';
                }
                field(displayName; Rec.Description)  // Descriptive
                {
                    Caption = 'Display Name';
                }
                field(unitPrice; Rec."Unit Price")  // Descriptive
                {
                    Caption = 'Unit Price';
                }
                field(inventoryQuantity; Rec.Inventory)  // Descriptive
                {
                    Caption = 'Inventory Quantity';
                }
            }
        }
    }
}
```

**Incorrect Example**:
```al
page 50100 "VOL Item API"
{
    PageType = API;
    SourceTable = Item;

    layout
    {
        area(Content)
        {
            repeater(General)
            {
                field(code; Rec."No.")  // VIOLATION: Not descriptive
                {
                }
                field(name; Rec.Description)  // Could be more specific
                {
                }
                field(value; Rec."Unit Price")  // VIOLATION: Not descriptive
                {
                }
            }
        }
    }
}
```

## LC0064: Table Field Missing ToolTip (Info)

**Rule**: A value for the ToolTip property is missing for the table field.

**Why**: Table field ToolTips:
- Provide documentation at the data model level
- Can be inherited by page fields
- Improve user experience through consistent help text

**Instruction**: Add ToolTip to table fields, especially those displayed on pages.

**Correct Example**:
```al
table 50100 "VOL Sales Document"
{
    Caption = 'Sales Document';

    fields
    {
        field(1; "No."; Code[20])
        {
            Caption = 'No.';
            ToolTip = 'Specifies the unique document number.';
        }
        field(10; "Customer No."; Code[20])
        {
            Caption = 'Customer No.';
            ToolTip = 'Specifies the customer who will receive the goods or services.';
            TableRelation = Customer;
        }
        field(20; "Posting Date"; Date)
        {
            Caption = 'Posting Date';
            ToolTip = 'Specifies the date when the document will be posted to the ledger.';
        }
        field(30; Amount; Decimal)
        {
            Caption = 'Amount';
            ToolTip = 'Specifies the total amount including VAT for the document.';
        }
    }
}
```

## LC0065: Event Subscriber Var Check (Warning)

**Rule**: Parameter '{0}' must use the 'var' keyword if the publisher uses it.

**Why**: If an event publisher declares a parameter as 'var' (by reference), subscribers must also use 'var'. Otherwise, changes made by the subscriber won't be reflected in the original variable.

**Instruction**: Match the 'var' keyword usage between publisher and subscriber.

**Correct Example**:
```al
// Publisher (in base codeunit)
[IntegrationEvent(false, false)]
procedure OnBeforeValidate(var SalesLine: Record "Sales Line"; var IsHandled: Boolean)
begin
end;

// Subscriber - matches publisher's var keywords
[EventSubscriber(ObjectType::Codeunit, Codeunit::"Sales-Post", OnBeforeValidate, '', false, false)]
local procedure HandleOnBeforeValidate(var SalesLine: Record "Sales Line"; var IsHandled: Boolean)
begin
    // Can modify SalesLine and IsHandled
    if SalesLine.Quantity > 1000 then
        IsHandled := true;
end;
```

**Incorrect Example**:
```al
// Publisher has 'var SalesLine'
[IntegrationEvent(false, false)]
procedure OnBeforeValidate(var SalesLine: Record "Sales Line"; var IsHandled: Boolean)
begin
end;

// VIOLATION: Missing 'var' on SalesLine
[EventSubscriber(ObjectType::Codeunit, Codeunit::"Sales-Post", OnBeforeValidate, '', false, false)]
local procedure HandleOnBeforeValidate(SalesLine: Record "Sales Line"; var IsHandled: Boolean)
begin
    // Changes to SalesLine won't be reflected!
    SalesLine.Quantity := 0;  // This modification is lost
end;
```

## LC0066: Duplicate ToolTip Between Page And Table (Info)

**Rule**: The ToolTip property of page field {0} and table field {1} are same.

**Why**: When page and table field ToolTips are identical, specifying it on the page is redundant. The page field can inherit from the table field.

**Instruction**: Remove duplicate ToolTips from page fields when they match the table field.

**Correct Example**:
```al
// Table with ToolTip
table 50100 "VOL Item"
{
    fields
    {
        field(10; Description; Text[100])
        {
            Caption = 'Description';
            ToolTip = 'Specifies the description of the item.';
        }
    }
}

// Page - no need to repeat ToolTip
page 50100 "VOL Item Card"
{
    SourceTable = "VOL Item";

    layout
    {
        area(Content)
        {
            field(Description; Rec.Description)
            {
                // ToolTip inherited from table field
            }
        }
    }
}
```

**When Page ToolTip Should Differ**:
```al
page 50100 "VOL Item Card"
{
    SourceTable = "VOL Item";

    layout
    {
        area(Content)
        {
            field(Description; Rec.Description)
            {
                // Different ToolTip - provides page-specific context
                ToolTip = 'Specifies the description that appears on sales documents.';
            }
        }
    }
}
```

## LC0067: Disable NotBlank On Single Field Primary Key (Warning)

**Rule**: The NotBlank property should be set to false if TableRelation of 'No. Series' exists.

**Why**: When a primary key field has a TableRelation to "No. Series", the number is auto-generated. NotBlank = true would prevent users from leaving the field empty for auto-numbering.

**Instruction**: Set NotBlank = false when the field uses No. Series for automatic numbering.

**Correct Example**:
```al
table 50100 "VOL Sales Document"
{
    fields
    {
        field(1; "No."; Code[20])
        {
            Caption = 'No.';
            NotBlank = false;  // Allow empty for No. Series auto-generation
            TableRelation = "No. Series";
        }
    }

    trigger OnInsert()
    var
        NoSeriesMgt: Codeunit "No. Series";
    begin
        if "No." = '' then
            "No." := NoSeriesMgt.GetNextNo(GetNoSeriesCode(), WorkDate(), true);
    end;
}
```

**Incorrect Example**:
```al
table 50100 "VOL Sales Document"
{
    fields
    {
        field(1; "No."; Code[20])
        {
            Caption = 'No.';
            NotBlank = true;  // VIOLATION: Conflicts with No. Series usage
            TableRelation = "No. Series";
        }
    }
}
```

## LC0068: Check Object Permission (Info)

**Rule**: The current object is missing permission "{0}" for tabledata "{1}".

**Why**: If code accesses a table but the permission set doesn't include that table, users will get permission errors at runtime.

**Instruction**: Ensure permission sets cover all tables accessed by your code.

**Correct Example**:
```al
codeunit 50100 "VOL Sales Manager"
{
    procedure ProcessSales()
    var
        SalesHeader: Record "Sales Header";
        SalesLine: Record "Sales Line";
    begin
        // Code accesses both tables
        SalesHeader.FindSet();
        SalesLine.SetRange("Document No.", SalesHeader."No.");
    end;
}

// Permission set must include both tables
permissionset 50100 "VOL Sales"
{
    Permissions =
        tabledata "Sales Header" = RIMD,
        tabledata "Sales Line" = RIMD,
        codeunit "VOL Sales Manager" = X;
}
```

## LC0069: Empty Statements (Info)

**Rule**: Empty statements should be avoided or should have a comment.

**Why**: Empty statements (like lone semicolons or empty begin/end blocks) are usually mistakes. If intentional, they need explanation.

**Instruction**: Remove empty statements or add comments explaining why they're needed.

**Correct Example**:
```al
procedure ProcessItems()
var
    Item: Record Item;
begin
    if Item.FindSet() then
        repeat
            ProcessItem(Item);
        until Item.Next() = 0;
    // Note: No else needed - empty result set is valid
end;

procedure InitializeWithComment()
begin
    // Intentionally empty - initialization handled by triggers
end;
```

**Incorrect Example**:
```al
procedure ProcessItems()
var
    Item: Record Item;
begin
    if Item.FindSet() then
        repeat
            ProcessItem(Item);
        until Item.Next() = 0
    else
        ;  // VIOLATION: Empty statement without explanation

    begin
    end;  // VIOLATION: Empty block
end;
```

## LC0070: List Objects Are One Based (Warning)

**Rule**: List objects are 1-based. Zero index access is invalid.

**Why**: Unlike arrays in many languages, AL List objects use 1-based indexing. Accessing index 0 causes a runtime error.

**Instruction**: ALWAYS use 1-based indexing with List objects.

**Correct Example**:
```al
procedure ProcessList()
var
    CustomerList: List of [Code[20]];
    i: Integer;
    CustomerNo: Code[20];
begin
    CustomerList.Add('CUST001');
    CustomerList.Add('CUST002');
    CustomerList.Add('CUST003');

    // Correct: 1-based access
    CustomerNo := CustomerList.Get(1);  // Gets 'CUST001'

    // Correct: Loop from 1
    for i := 1 to CustomerList.Count do
        ProcessCustomer(CustomerList.Get(i));

    // Correct: foreach
    foreach CustomerNo in CustomerList do
        ProcessCustomer(CustomerNo);
end;
```

**Incorrect Example**:
```al
procedure ProcessList()
var
    CustomerList: List of [Code[20]];
    CustomerNo: Code[20];
begin
    CustomerList.Add('CUST001');

    // VIOLATION: Zero-based access - will cause runtime error
    CustomerNo := CustomerList.Get(0);

    // VIOLATION: Starting loop at 0
    for i := 0 to CustomerList.Count - 1 do
        ProcessCustomer(CustomerList.Get(i));
end;
```
