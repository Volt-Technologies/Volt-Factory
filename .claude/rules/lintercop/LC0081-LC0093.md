# LinterCop Rules LC0081-LC0093

## LC0081: Use IsEmpty Method (Info)

**Rule**: Avoid using {0}.Count() for checking record existence. Use Rec.IsEmpty() instead.

**Why**: Count() reads all matching records to count them. IsEmpty() stops at the first record found, making it much more efficient.

**Instruction**: Use IsEmpty() or not IsEmpty() instead of Count() > 0 or Count() = 0.

**Correct Example**:
```al
procedure HasOpenOrders(CustomerNo: Code[20]): Boolean
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.SetRange("Sell-to Customer No.", CustomerNo);
    SalesHeader.SetRange(Status, SalesHeader.Status::Open);
    exit(not SalesHeader.IsEmpty());  // Efficient - stops at first record
end;

procedure EnsureNoOpenOrders(CustomerNo: Code[20])
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.SetRange("Sell-to Customer No.", CustomerNo);
    SalesHeader.SetRange(Status, SalesHeader.Status::Open);
    if not SalesHeader.IsEmpty() then
        Error(OpenOrdersExistErr);
end;
```

**Incorrect Example**:
```al
procedure HasOpenOrders(CustomerNo: Code[20]): Boolean
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.SetRange("Sell-to Customer No.", CustomerNo);
    SalesHeader.SetRange(Status, SalesHeader.Status::Open);
    exit(SalesHeader.Count() > 0);  // VIOLATION: Counts all records unnecessarily
end;

procedure GetOrderCount(CustomerNo: Code[20])
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.SetRange("Sell-to Customer No.", CustomerNo);
    if SalesHeader.Count() = 0 then  // VIOLATION: Use IsEmpty()
        Message('No orders');
end;
```

## LC0082: Use Query Or Find With Next (Info)

**Rule**: Consider using a Query object or {0}.Find('-') together with {0}.Next() for better performance.

**Why**: For large datasets, Query objects or Find('-')/Next() combinations can be more efficient than FindSet() for certain operations.

**Instruction**: For complex aggregations or when processing large datasets, consider Query objects. For simple iterations where you need to modify records, FindSet() with Next() is appropriate.

**Correct Example for Aggregation**:
```al
query 50100 "VOL Customer Totals"
{
    QueryType = Normal;

    elements
    {
        dataitem(SalesHeader; "Sales Header")
        {
            column(CustomerNo; "Sell-to Customer No.") { }
            column(TotalAmount; Amount)
            {
                Method = Sum;
            }
            column(OrderCount; "No.")
            {
                Method = Count;
            }
        }
    }
}
```

**Correct Example for Simple Iteration**:
```al
procedure ProcessOrders()
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.SetRange(Status, SalesHeader.Status::Open);
    if SalesHeader.Find('-') then
        repeat
            ProcessOrder(SalesHeader);
        until SalesHeader.Next() = 0;
end;
```

**When to Use Each**:
- **Query**: Aggregations (Sum, Count, Avg), grouped results, read-only operations
- **FindSet()**: When modifying records during iteration
- **Find('-')/Next()**: Simple iteration without modification

## LC0083: Built In DateTime Method (Info)

**Rule**: Use the new method {0}.{1} to extract specific parts.

**Why**: Modern AL provides methods directly on Date, Time, and DateTime types. These are clearer than the older Date2DMY/Date2DWY functions.

**Instruction**: Use the new Date/Time/DateTime methods for extracting parts.

**Correct Example**:
```al
procedure GetDateParts(InputDate: Date)
var
    Day: Integer;
    Month: Integer;
    Year: Integer;
    DayOfWeek: Integer;
begin
    // Modern approach - clearer and more readable
    Year := Date2DMY(InputDate, 3);
    Month := Date2DMY(InputDate, 2);
    Day := Date2DMY(InputDate, 1);

    // For DateTime
    Today := CurrentDateTime;
    Year := DT2Date(Today);
end;
```

**Note**: The exact new methods depend on the AL runtime version. Check Microsoft documentation for your runtime version.

## LC0084: Use Return Value For Error Handling (Info)

**Rule**: The return value of the '{0}' method must be used.

**Why**: Some methods return values that indicate success or failure. Ignoring these return values can lead to silent failures and data integrity issues.

**Instruction**: Always check return values of methods that indicate success/failure.

**Correct Example**:
```al
procedure SafeGetCustomer(CustomerNo: Code[20]; var Customer: Record Customer): Boolean
begin
    // Return value used
    exit(Customer.Get(CustomerNo));
end;

procedure ProcessCustomer(CustomerNo: Code[20])
var
    Customer: Record Customer;
begin
    // Check return value
    if not Customer.Get(CustomerNo) then
        Error(CustomerNotFoundErr, CustomerNo);

    ProcessCustomerData(Customer);
end;

procedure TryModify()
var
    Customer: Record Customer;
begin
    // Check Modify return value
    if not Customer.Modify() then
        Error(ModifyFailedErr);
end;
```

**Incorrect Example**:
```al
procedure ProcessCustomer(CustomerNo: Code[20])
var
    Customer: Record Customer;
begin
    Customer.Get(CustomerNo);  // VIOLATION: Return value ignored
    // If customer doesn't exist, next line causes error
    ProcessCustomerData(Customer);
end;

procedure TryModify()
var
    Customer: Record Customer;
begin
    Customer.Modify();  // VIOLATION: Return value ignored
    // Don't know if it succeeded
end;
```

## LC0085: LF Separator (Info)

**Rule**: Use the (CR)LFSeparator from the "Type Helper" codeunit.

**Why**: Using the Type Helper codeunit's constants ensures correct line separators across platforms and maintains consistency.

**Instruction**: Use Type Helper codeunit for line break constants.

**Correct Example**:
```al
procedure FormatMultilineText(): Text
var
    TypeHelper: Codeunit "Type Helper";
    ResultText: Text;
begin
    ResultText := 'Line 1' + TypeHelper.CRLFSeparator() + 'Line 2';
    // or for LF only:
    ResultText := 'Line 1' + TypeHelper.LFSeparator() + 'Line 2';
    exit(ResultText);
end;
```

**Incorrect Example**:
```al
procedure FormatMultilineText(): Text
var
    ResultText: Text;
begin
    // VIOLATION: Hardcoded line break characters
    ResultText := 'Line 1' + '\n' + 'Line 2';
    // or
    ResultText := 'Line 1
Line 2';  // Embedded line break
    exit(ResultText);
end;
```

## LC0086: PageStyle DataType (Info)

**Rule**: Avoid using the string literal '{0}' for page styling. Use the new PageStyle datatype instead.

**Why**: The PageStyle datatype provides compile-time checking and IntelliSense support. String literals can contain typos that won't be caught until runtime.

**Instruction**: Use PageStyle enum values instead of string literals.

**Correct Example**:
```al
page 50100 "VOL Customer List"
{
    SourceTable = Customer;

    layout
    {
        area(Content)
        {
            repeater(General)
            {
                field("No."; Rec."No.")
                {
                    StyleExpr = StyleTxt;
                }
            }
        }
    }

    var
        StyleTxt: Text;

    trigger OnAfterGetRecord()
    begin
        // Use enum values for styling
        if Rec.Blocked <> Rec.Blocked::" " then
            StyleTxt := Format(Enum::PageStyle::Unfavorable)
        else
            StyleTxt := Format(Enum::PageStyle::None);
    end;
}
```

**Incorrect Example**:
```al
trigger OnAfterGetRecord()
begin
    // VIOLATION: String literals for styles
    if Rec.Blocked <> Rec.Blocked::" " then
        StyleTxt := 'Unfavorable'  // Could have typo
    else
        StyleTxt := 'Standard';  // Could have typo
end;
```

## LC0087: Use IsNullGuid (Warning)

**Rule**: Use 'IsNullGuid({0})' method instead of comparing with empty GUID.

**Why**: IsNullGuid() is the proper way to check for empty GUIDs. Direct comparison can have issues with GUID representations.

**Instruction**: ALWAYS use IsNullGuid() to check for empty GUIDs.

**Correct Example**:
```al
procedure HasSystemId(var Record: Record "Sales Header"): Boolean
begin
    exit(not IsNullGuid(Record.SystemId));
end;

procedure ValidateGuid(InputGuid: Guid)
begin
    if IsNullGuid(InputGuid) then
        Error(GuidRequiredErr);
end;
```

**Incorrect Example**:
```al
procedure HasSystemId(var Record: Record "Sales Header"): Boolean
var
    EmptyGuid: Guid;
begin
    exit(Record.SystemId <> EmptyGuid);  // VIOLATION: Use IsNullGuid()
end;

procedure ValidateGuid(InputGuid: Guid)
begin
    if InputGuid = '' then  // VIOLATION: Use IsNullGuid()
        Error(GuidRequiredErr);
end;
```

## LC0088: Avoid Option Types (Info)

**Rule**: Option types should be avoided, use enum if applicable.

**Why**: Enums provide:
- Type safety
- Extensibility by other apps
- Better IntelliSense and documentation
- Reusability across objects

**Instruction**: Use Enum instead of Option for new development.

**Correct Example**:
```al
enum 50100 "VOL Document Status"
{
    Extensible = true;

    value(0; " ") { Caption = ' '; }
    value(1; Open) { Caption = 'Open'; }
    value(2; Released) { Caption = 'Released'; }
    value(3; Closed) { Caption = 'Closed'; }
}

table 50100 "VOL Document"
{
    fields
    {
        field(10; Status; Enum "VOL Document Status")  // Use Enum
        {
            Caption = 'Status';
        }
    }
}
```

**Incorrect Example**:
```al
table 50100 "VOL Document"
{
    fields
    {
        field(10; Status; Option)  // VIOLATION: Use Enum instead
        {
            Caption = 'Status';
            OptionMembers = " ",Open,Released,Closed;
            OptionCaption = ' ,Open,Released,Closed';
        }
    }
}
```

## LC0089: Cognitive Complexity (Info)

**Rule**: Cognitive Complexity: {0} (threshold >={1})

**Why**: Cognitive complexity measures how difficult code is to understand. High cognitive complexity indicates code that's hard to maintain and prone to bugs.

**Instruction**: Keep cognitive complexity low by:
- Breaking down complex methods
- Reducing nesting levels
- Using early returns
- Extracting complex conditions into well-named methods

**High Complexity (Bad)**:
```al
procedure ComplexMethod(Customer: Record Customer)
begin
    if Customer.Blocked = Customer.Blocked::" " then begin
        if Customer."Credit Limit" > 0 then begin
            if GetOutstandingAmount(Customer) < Customer."Credit Limit" then begin
                if HasValidPaymentTerms(Customer) then begin
                    // Deep nesting increases cognitive complexity
                    ProcessOrder();
                end;
            end;
        end;
    end;
end;
```

**Low Complexity (Good)**:
```al
procedure SimplifiedMethod(Customer: Record Customer)
begin
    if not IsCustomerEligible(Customer) then
        exit;

    ProcessOrder();
end;

local procedure IsCustomerEligible(Customer: Record Customer): Boolean
begin
    if Customer.Blocked <> Customer.Blocked::" " then
        exit(false);
    if Customer."Credit Limit" = 0 then
        exit(false);
    if GetOutstandingAmount(Customer) >= Customer."Credit Limit" then
        exit(false);
    if not HasValidPaymentTerms(Customer) then
        exit(false);
    exit(true);
end;
```

## LC0091: Translatable Text Should Be Translated (Info)

**Rule**: {0} is missing a translation in languages: {1}.

**Why**: Labels and captions should be translated for international users. Missing translations result in the default language text being shown.

**Instruction**: Ensure all Label variables and Caption properties have translations for all supported languages.

**Correct Example**:
```al
var
    WelcomeMessageLbl: Label 'Welcome to the application', Comment = 'ESP="Bienvenido a la aplicación"';
    ErrorMessageLbl: Label 'An error occurred: %1', Comment = '%1 = Error details; ESP="Se produjo un error: %1"';
```

**Note**: Translation management typically uses XLIFF files. The Comment with translations is a simplified example.

## LC0092: Name Pattern (Info)

**Rule**: {0} name "{1}" must match/must not match pattern "{2}".

**Why**: Consistent naming patterns improve code readability and maintainability. Projects often enforce naming conventions.

**Instruction**: Follow the naming patterns defined in your project's LinterCop configuration.

**Common Patterns**:
- Object names with prefix: `VOL*`
- Interface names: `I*`
- Test codeunits: `*Test*`
- Event names: `On*`

## LC0093: Global Test Method Requires Test Attribute (Info)

**Rule**: Global procedure "{0}" in test codeunit requires [Test] attribute.

**Why**: In test codeunits, global (public) procedures should either be:
- Test methods with [Test] attribute
- Helper methods that should be local

**Instruction**: Add [Test] attribute to test procedures or make helper procedures local.

**Correct Example**:
```al
codeunit 50100 "VOL Sales Tests"
{
    Subtype = Test;

    [Test]
    [HandlerFunctions('ConfirmHandler')]
    procedure TestSalesOrderPosting()
    begin
        // Test implementation
        Initialize();
        CreateTestData();
        // Assert results
    end;

    [Test]
    procedure TestCustomerValidation()
    begin
        // Another test
    end;

    local procedure Initialize()  // Local helper
    begin
        // Setup code
    end;

    local procedure CreateTestData()  // Local helper
    begin
        // Create test records
    end;

    [ConfirmHandler]
    procedure ConfirmHandler(Question: Text; var Reply: Boolean)
    begin
        Reply := true;
    end;
}
```

**Incorrect Example**:
```al
codeunit 50100 "VOL Sales Tests"
{
    Subtype = Test;

    procedure TestSalesOrderPosting()  // VIOLATION: Missing [Test] attribute
    begin
        Initialize();
    end;

    procedure Initialize()  // VIOLATION: Helper should be local
    begin
        // Setup code
    end;
}
```
