# LinterCop Rules LC0011-LC0020

## LC0011: Access Property Should Always Be Set (Hidden)

**Rule**: Access property is missing!

**Why**: The Access property controls visibility of objects to other extensions. Explicitly setting it makes the API surface intentional rather than accidental.

**Instruction**: ALWAYS set the Access property on tables, codeunits, pages, and other objects. Use `Internal` unless the object needs to be accessible to other extensions.

**Correct Example**:
```al
table 50100 "VOL Internal Setup"
{
    Caption = 'Internal Setup';
    Access = Internal;  // Not accessible to other extensions

    fields { ... }
}

table 50101 "VOL Public API Data"
{
    Caption = 'Public API Data';
    Access = Public;  // Accessible to other extensions

    fields { ... }
}
```

## LC0012: Do Not Use Object ID In System Functions (Warning)

**Rule**: Wrong Parameter detected. Select the correct object with "{0}::"

**Why**: Using object IDs in system functions like Codeunit.Run or Report.Run makes code less readable and prone to errors if object IDs change.

**Instruction**: Use named object references with `::` notation instead of numeric IDs.

**Correct Example**:
```al
procedure RunReport()
begin
    Report.Run(Report::"Customer - Order Summary");
    Codeunit.Run(Codeunit::"Release Sales Document", SalesHeader);
end;
```

**Incorrect Example**:
```al
procedure RunReport()
begin
    Report.Run(107);  // VIOLATION: Use Report::"Customer - Order Summary"
    Codeunit.Run(414, SalesHeader);  // VIOLATION: Use Codeunit::"Release Sales Document"
end;
```

## LC0013: Check For NotBlank On Single Field Primary Keys (Warning)

**Rule**: NotBlank should be set explicitly for single-field primary key tables.

**Why**: Single-field primary keys (typically Code or Text fields) usually require a value. Making NotBlank explicit prevents accidental creation of records with blank keys.

**Instruction**: For tables with a single-field primary key of type Code or Text, ALWAYS set NotBlank = true on that field.

**Correct Example**:
```al
table 50100 "VOL Product Category"
{
    Caption = 'Product Category';

    fields
    {
        field(1; "Code"; Code[20])
        {
            Caption = 'Code';
            NotBlank = true;  // MANDATORY for single-field PK
        }
        field(2; Description; Text[100])
        {
            Caption = 'Description';
        }
    }

    keys
    {
        key(PK; "Code")
        {
            Clustered = true;
        }
    }
}
```

**Exception**: See LC0067 for No. Series fields where NotBlank should be false.

## LC0014: PermissionSet Caption Length (Warning)

**Rule**: The Caption of permissionset objects should not exceed the maximum length ({0} characters).

**Why**: Permission set captions are displayed in the UI and have a maximum length. Exceeding this limit causes truncation and confusion.

**Instruction**: Keep permission set captions under 30 characters.

**Correct Example**:
```al
permissionset 50100 "VOL Sales Full"
{
    Caption = 'VOL Sales Full Access';  // Under 30 characters
    Assignable = true;

    Permissions =
        tabledata "VOL Sales Setup" = RIMD,
        tabledata "VOL Sales Entry" = RIMD;
}
```

**Incorrect Example**:
```al
permissionset 50100 "VOL Sales Full"
{
    Caption = 'VOL Sales Full Access Permission Set for All Users';  // VIOLATION: Too long
    Assignable = true;
}
```

## LC0015: PermissionSet Coverage (Warning)

**Rule**: All application objects should be covered by at least one permission set. The application object {0} "{1}" is not covered by any permission set.

**Why**: Objects not covered by permission sets cannot be properly secured. Users won't be able to access them through normal permission assignment.

**Instruction**: Create permission sets that cover ALL your application objects. Group related objects logically.

**Correct Structure**:
```al
// Permission set covering all VOL objects
permissionset 50100 "VOL All Objects"
{
    Caption = 'VOL All Objects';
    Assignable = true;

    Permissions =
        tabledata "VOL Setup" = RIMD,
        tabledata "VOL Entry" = RIMD,
        table "VOL Setup" = X,
        table "VOL Entry" = X,
        codeunit "VOL Management" = X,
        page "VOL Setup Card" = X,
        page "VOL Entry List" = X,
        report "VOL Summary Report" = X;
}
```

## LC0016: Check For Missing Captions (Warning)

**Rule**: Caption is missing.

**Why**: Captions are displayed to users in the UI. Missing captions result in technical names being shown, which confuses users.

**Instruction**: ALWAYS provide Caption property for:
- Table fields
- Page fields
- Actions
- Groups
- Enum values
- Any UI-visible element

**Correct Example**:
```al
field(10; "Customer No."; Code[20])
{
    Caption = 'Customer No.';
    TableRelation = Customer;
}

action(Post)
{
    Caption = 'Post';
    Image = PostOrder;

    trigger OnAction()
    begin
        PostDocument();
    end;
}
```

**Incorrect Example**:
```al
field(10; "Customer No."; Code[20])
{
    // VIOLATION: Missing Caption
    TableRelation = Customer;
}
```

## LC0017: Writing To FlowField Requires Comment (Warning)

**Rule**: Writing to a FlowField is not common. Add a comment to explain this.

**Why**: FlowFields are calculated fields and normally shouldn't be written to directly. When this unusual pattern is necessary, it requires explanation.

**Instruction**: If you must write to a FlowField (rare), add a comment explaining why.

**Correct Example (if absolutely necessary)**:
```al
procedure SetCachedAmount()
begin
    // Writing to FlowField to cache the calculated value for performance
    // This is intentional as recalculating on every access is too slow
    Rec."Cached Total" := CalculatedAmount;
    Rec.Modify();
end;
```

**Better Approach**: Usually, avoid writing to FlowFields. Use a regular field instead if you need to store a value.

## LC0018: No Events In Internal Codeunits (Info)

**Rule**: Events in internal codeunits are not accessible to extensions. The event {0} is declared in an internal codeunit {1}.

**Why**: If a codeunit is marked as Internal, other extensions cannot access it, including its events. Publishing events from internal codeunits is pointless.

**Instruction**: If you need to publish events that other extensions can subscribe to, the codeunit must have `Access = Public`.

**Correct Example**:
```al
codeunit 50100 "VOL Sales Events"
{
    Access = Public;  // Required for events to be subscribable

    [IntegrationEvent(false, false)]
    procedure OnBeforePostSalesDocument(var SalesHeader: Record "Sales Header")
    begin
    end;
}
```

**Incorrect Example**:
```al
codeunit 50100 "VOL Sales Events"
{
    Access = Internal;  // Events won't be accessible

    [IntegrationEvent(false, false)]
    procedure OnBeforePostSalesDocument(var SalesHeader: Record "Sales Header")
    begin
        // VIOLATION: This event is useless - no one can subscribe to it
    end;
}
```

## LC0019: DataClassification Field Equals Table (Info)

**Rule**: Data Classification is equal to the Table. Remove to reduce redundancy.

**Why**: When a field's DataClassification matches the table's DataClassification, specifying it on the field is redundant. This creates maintenance burden.

**Instruction**: Only specify DataClassification on fields when it differs from the table's classification.

**Correct Example**:
```al
table 50100 "VOL Customer Data"
{
    Caption = 'Customer Data';
    DataClassification = CustomerContent;  // Table default

    fields
    {
        field(1; "Code"; Code[20])
        {
            Caption = 'Code';
            // No DataClassification needed - inherits from table
        }
        field(2; "Social Security No."; Text[20])
        {
            Caption = 'Social Security No.';
            DataClassification = EndUserIdentifiableInformation;  // Different from table
        }
    }
}
```

**Incorrect Example**:
```al
table 50100 "VOL Customer Data"
{
    Caption = 'Customer Data';
    DataClassification = CustomerContent;

    fields
    {
        field(1; "Code"; Code[20])
        {
            Caption = 'Code';
            DataClassification = CustomerContent;  // VIOLATION: Redundant
        }
    }
}
```

## LC0020: ApplicationArea Equals To Page (Info)

**Rule**: Application Area is equal to the Page. Remove to reduce redundancy.

**Why**: When a control's ApplicationArea matches the page's ApplicationArea, specifying it on the control is redundant.

**Instruction**: Only specify ApplicationArea on controls when it differs from the page's setting.

**Correct Example**:
```al
page 50100 "VOL Sales List"
{
    Caption = 'Sales List';
    ApplicationArea = All;  // Page default

    layout
    {
        area(Content)
        {
            group(General)
            {
                field("No."; Rec."No.")
                {
                    // ApplicationArea inherited from page
                }
                field("Premium Feature"; Rec."Premium Feature")
                {
                    ApplicationArea = Premium;  // Different from page
                }
            }
        }
    }
}
```

**Incorrect Example**:
```al
page 50100 "VOL Sales List"
{
    Caption = 'Sales List';
    ApplicationArea = All;

    layout
    {
        area(Content)
        {
            field("No."; Rec."No.")
            {
                ApplicationArea = All;  // VIOLATION: Redundant
            }
        }
    }
}
```
