# LinterCop Rules LC0031-LC0040

## LC0031: Record Instance Isolation Level (Info)

**Rule**: Use ReadIsolation(IsolationLevel::UpdLock) instead of LockTable().

**Why**: ReadIsolation provides more granular control over locking behavior and is the modern approach in Business Central. It allows specifying the isolation level at the record instance level.

**Instruction**: Replace LockTable() with ReadIsolation for better lock control.

**Correct Example**:
```al
procedure UpdateWithLock()
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.ReadIsolation := IsolationLevel::UpdLock;
    if SalesHeader.Get(SalesHeader."Document Type"::Order, OrderNo) then begin
        SalesHeader.Status := SalesHeader.Status::Released;
        SalesHeader.Modify();
    end;
end;
```

**Incorrect Example**:
```al
procedure UpdateWithLock()
var
    SalesHeader: Record "Sales Header";
begin
    SalesHeader.LockTable();  // VIOLATION: Use ReadIsolation instead
    if SalesHeader.Get(SalesHeader."Document Type"::Order, OrderNo) then begin
        SalesHeader.Status := SalesHeader.Status::Released;
        SalesHeader.Modify();
    end;
end;
```

## LC0032: Clear Codeunit Single Instance (Warning)

**Rule**: Clear(All) does not affect or change values for global variables in codeunits marked as SingleInstance.

**Why**: SingleInstance codeunits maintain their state across the session. Clear(All) does not affect these codeunits, which can lead to unexpected behavior if you expect the state to be cleared.

**Instruction**: Explicitly clear SingleInstance codeunit variables or provide a Reset procedure.

**Correct Example**:
```al
codeunit 50100 "VOL Cache Manager"
{
    SingleInstance = true;

    var
        CachedData: Dictionary of [Text, Text];

    procedure ClearCache()
    begin
        Clear(CachedData);  // Explicit clear
    end;

    procedure Reset()
    begin
        Clear(CachedData);
        // Clear all other state
    end;
}

// Usage:
procedure ResetAll()
var
    CacheManager: Codeunit "VOL Cache Manager";
begin
    CacheManager.Reset();  // Explicitly reset the singleton
    Clear(All);  // Clear other variables
end;
```

**Incorrect Example**:
```al
procedure ResetEverything()
begin
    Clear(All);  // WARNING: Won't clear SingleInstance codeunit state!
end;
```

## LC0033: AppManifest Runtime Behind (Info)

**Rule**: The specified runtime version in app.json is falling behind.

**Why**: Using an outdated runtime version means you miss new language features, performance improvements, and bug fixes. Staying current is important for security and functionality.

**Instruction**: Keep the runtime version in app.json up to date with the latest stable version.

**Correct Example** (app.json):
```json
{
    "id": "...",
    "name": "VOL Extension",
    "version": "1.0.0.0",
    "runtime": "14.0"
}
```

**Action**: Regularly review and update the runtime version when new BC versions are released.

## LC0034: Extensible Property Should Always Be Set (Hidden)

**Rule**: The property Extensible should be explicitly set for objects.

**Why**: The Extensible property determines whether other extensions can extend your objects. Explicitly setting this makes your API surface intentional.

**Instruction**: ALWAYS set the Extensible property on tables, pages, enums, and other extensible objects.

**Correct Example**:
```al
table 50100 "VOL Core Setup"
{
    Caption = 'Core Setup';
    Extensible = false;  // Cannot be extended by other apps

    fields { ... }
}

table 50101 "VOL Master Data"
{
    Caption = 'Master Data';
    Extensible = true;  // Can be extended by other apps

    fields { ... }
}

enum 50100 "VOL Status"
{
    Caption = 'Status';
    Extensible = true;  // Other apps can add values

    value(0; Open) { Caption = 'Open'; }
    value(1; Released) { Caption = 'Released'; }
}
```

## LC0035: Explicit Set AllowInCustomizations (Info)

**Rule**: Explicitly set AllowInCustomizations for fields omitted on pages.

**Why**: When table fields aren't shown on pages, the AllowInCustomizations property determines whether users can add them via personalization. Being explicit prevents unintended exposure of internal fields.

**Instruction**: Set AllowInCustomizations on fields that should or shouldn't be user-customizable.

**Correct Example**:
```al
table 50100 "VOL Document"
{
    fields
    {
        field(1; "No."; Code[20])
        {
            Caption = 'No.';
            AllowInCustomizations = Always;  // Users can add to any page
        }
        field(10; "Internal Code"; Code[10])
        {
            Caption = 'Internal Code';
            AllowInCustomizations = Never;  // Internal - hide from users
        }
    }
}
```

## LC0036: ToolTip Should Start With Specifies (Info)

**Rule**: ToolTip must start with the verb "Specifies".

**Why**: Microsoft documentation standards require tooltips to start with "Specifies" for consistency across the platform.

**Instruction**: ALL ToolTip values must start with "Specifies".

**Correct Example**:
```al
field("Customer No."; Rec."Customer No.")
{
    ToolTip = 'Specifies the number of the customer associated with this document.';
}

field(Amount; Rec.Amount)
{
    ToolTip = 'Specifies the total amount including VAT.';
}

field("Posting Date"; Rec."Posting Date")
{
    ToolTip = 'Specifies the date when the document will be posted to the general ledger.';
}
```

**Incorrect Example**:
```al
field("Customer No."; Rec."Customer No.")
{
    ToolTip = 'The customer number for this document.';  // VIOLATION: Start with "Specifies"
}

field(Amount; Rec.Amount)
{
    ToolTip = 'Shows the total amount.';  // VIOLATION: Start with "Specifies"
}
```

## LC0037: ToolTip Do Not Use Line Breaks (Info)

**Rule**: Do not use line breaks in ToolTip.

**Why**: Line breaks in tooltips display incorrectly in the BC client and create formatting issues.

**Instruction**: Keep ToolTip text on a single logical line without line breaks.

**Correct Example**:
```al
field(Description; Rec.Description)
{
    ToolTip = 'Specifies a description of the item. This description appears on all sales and purchase documents.';
}
```

**Incorrect Example**:
```al
field(Description; Rec.Description)
{
    ToolTip = 'Specifies a description of the item.\nThis description appears on all sales documents.';
    // VIOLATION: Contains line break
}
```

## LC0038: ToolTip Maximum Length (Info)

**Rule**: Try to not exceed 200 characters (including spaces).

**Why**: Long tooltips get truncated in the UI and are difficult to read. Concise tooltips are more effective.

**Instruction**: Keep ToolTip text under 200 characters.

**Correct Example**:
```al
field("Expected Receipt Date"; Rec."Expected Receipt Date")
{
    ToolTip = 'Specifies the expected date when items will arrive at the warehouse.';
    // 74 characters - good
}
```

**Incorrect Example**:
```al
field("Expected Receipt Date"; Rec."Expected Receipt Date")
{
    ToolTip = 'Specifies the expected date when the items on this purchase order line are expected to arrive at the warehouse location specified in the Location Code field based on the vendor lead time and order date.';
    // VIOLATION: 229 characters - too long
}
```

## LC0039: Argument Different Type Than Expected (Warning)

**Rule**: Argument {0}: cannot convert from {1} to {2}.

**Why**: Type mismatches can cause runtime errors or unexpected behavior. The compiler should catch these issues.

**Instruction**: Ensure procedure arguments match the expected types. Use explicit type conversions when necessary.

**Correct Example**:
```al
procedure ProcessQuantity(Qty: Decimal)
begin
    // ...
end;

// Usage:
var
    Quantity: Decimal;
begin
    Quantity := 10.5;
    ProcessQuantity(Quantity);  // Correct: Decimal to Decimal
end;
```

**Incorrect Example**:
```al
procedure ProcessQuantity(Qty: Decimal)
begin
    // ...
end;

// Usage:
var
    QuantityText: Text;
begin
    QuantityText := '10.5';
    ProcessQuantity(QuantityText);  // VIOLATION: Text to Decimal
end;
```

## LC0040: Explicitly Set RunTrigger (Info)

**Rule**: Explicitly set the RunTrigger parameter on build-in methods.

**Why**: Methods like Insert, Modify, Delete, and Rename have an optional RunTrigger parameter. Being explicit about whether triggers should run prevents unexpected behavior.

**Instruction**: ALWAYS specify the RunTrigger parameter on Insert, Modify, Delete, and Rename calls.

**Correct Example**:
```al
procedure CreateRecord()
var
    MyRecord: Record "VOL My Table";
begin
    MyRecord.Init();
    MyRecord."No." := GetNextNo();
    MyRecord.Insert(true);  // Explicit: Run triggers

    // or
    MyRecord.Insert(false);  // Explicit: Don't run triggers
end;

procedure UpdateRecord()
var
    MyRecord: Record "VOL My Table";
begin
    if MyRecord.Get(RecordNo) then begin
        MyRecord.Description := 'Updated';
        MyRecord.Modify(true);  // Explicit: Run triggers
    end;
end;

procedure RemoveRecord()
var
    MyRecord: Record "VOL My Table";
begin
    if MyRecord.Get(RecordNo) then
        MyRecord.Delete(false);  // Explicit: Don't run triggers (for performance)
end;
```

**Incorrect Example**:
```al
procedure CreateRecord()
var
    MyRecord: Record "VOL My Table";
begin
    MyRecord.Init();
    MyRecord."No." := GetNextNo();
    MyRecord.Insert();  // VIOLATION: Is RunTrigger true or false?
end;
```
